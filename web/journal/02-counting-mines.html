Before the neural network could learn to guess, we built something that could count. The distinction becomes important when several plausible boards all fit the same clues.

A clue is an equation

An opened number says how many adjacent cells contain mines. Subtract mines already accounted for, and the remaining unknown neighbours must contain the remainder. Represent each unknown cell by a binary variable: zero for safe, one for a mine. Every visible clue supplies a sum constraint over some of those variables. The solver’s task is to find assignments that satisfy all the equations simultaneously.

A single clue is easy. Overlapping clues do the interesting work. If two equations share most of their cells, their difference can pin down another cell. But local deductions are not the whole problem: sometimes several assignments survive, with no cell forced. We still want probabilities. “I could not prove anything” is not the same statement as “all moves are equally good.”

Divide the frontier

The frontier consists of unknown cells touching visible clues. Build connections through the constraints, and it separates into components that can be enumerated independently. Within each component, backtracking tries mine assignments and rejects branches that cannot satisfy the clues. Rejecting impossible partial assignments avoids completing every binary arrangement just to discover that the first clue was already broken.

This is exact counting, not a learned approximation. For each component, the solver needs to know how many valid assignments use each possible number of mines, and how often each cell is mined within those assignments. Keeping the mine-count distribution is essential. Two components can be locally independent while still competing for the same global supply of mines.

Unknown cells outside the frontier form the interior. With no adjacent clues distinguishing them, the combinatorial count of ways to place the leftover mines matters. Let R be the remaining mines, K the mines allocated across the frontier components, and I the number of interior cells. The interior contributes a weight of C(I, R − K): the number of ways to choose those remaining mine locations.

Possibility is not probability

Here is a deliberately hypothetical example, not a measurement from a training run. Suppose one frontier assignment leaves room for many interior arrangements, while another leaves room for only one. Counting the two frontier assignments as equally likely would throw away most of the compatible full boards. The combinatorial weight is how the global mine count reaches back into apparently local probabilities.

The solver combines the components with those weights and normalizes the counts. A cell’s mine probability becomes the weighted fraction of compatible layouts in which it is mined. This also explains why hand-wiring exact inference into a few neural layers was not the easy escape hatch it first sounded like. The work is not merely recognizing a small visual pattern. It includes constraint enumeration and global counting.

The implementation was checked against brute force. That is a particularly useful relationship between two algorithms: a slow, simple enumerator can serve as a correctness reference for the cleverer version on tractable boards. A fast wrong probability is not a useful optimization, especially when it becomes the teacher for a network.

One solver, several responsibilities

Exact inference supports more than the greedy opponent. It supplies soft mine targets for training and generates consistent hidden layouts for search. “Soft” means a probability label rather than pretending every uncertain cell has a known binary answer. A fifty-fifty cell should not be taught as definitely safe merely because one sampled board happened to leave it empty.

Sampling has the same obligation as counting: it must respect both the visible constraints and the remaining mine total. Search can then ask what a move does across plausible worlds. It must not treat the sampled layout as information the player actually acquired. The sample is a simulation tool, not a licence to peek.

Exact does not mean constant-time

An early solver timing was roughly 0.35 milliseconds per 16×16 position. Later solver-game positions had a median around one millisecond, with frontiers of roughly 50 cells and up to thousands of solutions. These are different workloads, not two interchangeable stopwatch readings. Frontier structure determines how much enumeration there is to do.

When the user asked about one microsecond, the honest answer was no: roughly 3,000 CPU cycles is a very small budget for that work. More importantly, profiling later put the solver at only about one percent of self-play time. We had built a useful exact teacher. Making its stopwatch display a more glamorous unit was not the next best lesson.
