The project’s least sophisticated failure mode was also its most educational: a worker accidentally emptied app.js before there were any commits. Neural networks were not required.

The disappearing interface

The web interface was built and checked with headless Chromium screenshots. During cleanup, a worker tried to remove duplicated lines and instead emptied web/app.js. No git commits existed yet. The application script had to be rewritten from scratch. It was a blunt demonstration that an AI-assisted workflow does not exempt anyone from the oldest useful advice in software development: commit early.

The director-and-workers arrangement can make parallel construction convenient, but delegation is not a backup system. A task description can explain the intended edit; it cannot recover an uncommitted file after an incorrect edit destroys it. The human user’s direction, the director’s integration work, and the workers’ changes still need ordinary version-control boundaries.

This is also why the journal tells the story in terms of a user directing agents. “The AI built it” compresses away the questions, corrections, reviews, and recoveries that made the result possible. The script incident was not an amusing side effect of a magical process. It was a preventable engineering mistake in a very recognizable development process.

When zero looks like unknown

Some mistakes were visual rather than destructive. Revealed zero cells initially looked like unknown cells. That is not a cosmetic distinction in Minesweeper: covered cells are potential actions, and revealed blanks are evidence. Tooltips, clearer rules, explanation pages, and architecture diagrams all helped make the interface describe the game the engine was actually playing.

Later, changing status text made a card change size, producing header flicker during AI play. The fix used fixed-height rows rather than hoping the next message would be shorter. Measurements recorded constant card heights of 235 pixels, then 192 pixels after layout changes, across 100 samples during AI play. These are two layout stages, not simultaneous dimensions of the same card.

Hints moved into their own card, rules became a list, and the layout was simplified. The educational point is not that a particular pixel height is sacred. It is that visible stability can be measured. A layout that jumps every turn makes a strategic game harder to follow even when every game-state transition is correct.

A fraction below one

The first commits encountered a flaky test: a float32 softmax sum was 0.99999988 rather than exactly 1.0. The fix combined seeding with a tolerance. Floating-point arithmetic approximates real arithmetic; exact equality is often the wrong contract for a computed normalized distribution. That does not mean accepting arbitrary errors. It means specifying the numerical accuracy the algorithm actually promises.

Seeding controls the example being exercised; tolerance controls the numerical assertion. They address different sources of fragility. A deterministic but overly strict test can fail consistently for the wrong reason. A tolerant but uncontrolled test can still sample a different edge case each run. Neither tool replaces understanding what property the test is supposed to protect.

A cleanup task with excessive jurisdiction

A benchmark’s checkpoint retention reached into a live run directory and deleted iteration 97. It was harmless in that case because the checkpoint would have been pruned anyway, but the ownership boundary was wrong. The fix scoped deletion to the retention process’s own run directory and added a regression test. Global disk awareness did not justify global deletion authority.

The retention policy kept bootstraps, every tenth iteration, the newest three checkpoints, and pinned generations, with a 100 GB cap. Estimated growth was about 0.15 GB per day. Those policies manage useful history, but their implementation still needs to distinguish a production run from a disposable experiment. A benchmark should not tidy somebody else’s desk just because both desks are in the same room.

The run that stopped talking

The small control run died silently at iteration 69, without a traceback or OOM log. Six orphaned benchmark workers were each holding about 1.7 GB, roughly 10 GB of a 15 GB machine. That memory pressure was a serious operational clue, not a proved cause of death. The run was resumed exactly to iteration 82 before comparison.

That last step matters scientifically. Comparing a longer trial against a silently shortened control would mix a settings change with unequal training. Restoring the intended comparison was part of the experiment, not merely housekeeping. Later CPU-only workers and a shared GPU evaluator also made resource ownership easier to reason about.

The lessons are pleasantly unfashionable: preserve work, test numerical contracts, measure what users see, constrain cleanup authority, close worker pools, and compare like with like. The project needed hidden-information search and residual networks. It also needed someone to notice that a file had disappeared. Both kinds of work count.
