The user asked whether the exact solver could run in a microsecond. The profiler answered a more useful question: why were we discussing the one-percent slice?

The attractive wrong stopwatch

A microsecond is about 3,000 CPU cycles in the rough budget discussed during development. Exact frontier enumeration, with roughly 50 cells and potentially thousands of satisfying assignments, was not going to fit neatly inside that wish. Solver-game positions had a median around one millisecond. But the solver accounted for only about one percent of measured self-play time.

Network work and encoding consumed roughly 64%; layout sampling took another 15%. Optimizing the visibly clever algorithm would have left most of the cost untouched. This is the unglamorous benefit of profiling: it stops the most interesting function from automatically becoming the most important function.

Batched encoding became 14 times faster. Solver sampling was cached. Multiple worker processes increased game throughput by about 1.7 times in that phase. None of those numbers should be multiplied together as if they described independent speedups over the same whole program. Each belongs to a particular component or measured system configuration.

Search can waste a perfectly good tree

After an action, much of a previous search may still describe possible continuations. Tree reuse keeps only descendants matching the newly observed public board, scores, player, and bomb inventory. Extra turns mean the observed opponent continuation can span multiple levels. If no matching outcome exists, search starts fresh rather than forcing a convenient but wrong state.

No sampled hidden layout is retained as truth. Reuse preserves public-state search evidence, not an illicit memory of where a simulation put the mines. That restriction is both a fairness requirement and a correctness requirement: yesterday’s sampled possibility is not today’s observation.

Feed the GPU more than one leaf

A neural evaluator can process batches more efficiently than a sequence of tiny calls. Search, however, naturally asks for one leaf and waits for the answer. Virtual-loss batching reserves several leaves before making one network call. Temporary reservations discourage the in-progress selections from repeatedly choosing the same route; they are removed when the real evaluations arrive.

The chosen setting used K=4 leaves with PUCT-100 and tree reuse. It scored 57% against its own greedy policy and 49.5% against the old PUCT-100, while costing roughly 0.07 rather than 0.17 seconds per move in the comparison: about 2.4 times cheaper. The important result was comparable strength for less work, not an established strength breakthrough.

Workers also became CPU-only search processes sharing one GPU evaluator. Instead of each worker holding its own accelerator context and model state, requests were coalesced centrally. Two, four, and six workers produced approximately 35, 48, and 64 positions per second in the measured scaling test. Adding workers can help, but duplicated memory and scheduling are not free.

Benchmarks have environmental conditions

Python 3.12 versus 3.14 initially looked like a five-to-seven-percent slowdown under heavy load. The user preferred 3.14 for its future free-threading direction. A quieter repeat measured 51.5 versus 50.3 positions per second, within noise, and the project pinned Python 3.14. Free-threaded 3.14t worked with NumPy and Torch wheels but was not adopted.

The useful lesson is not that a preferred interpreter version must win a benchmark. It is that competing jobs can distort a small comparison. Repeating under quieter conditions answered the actual question better than arguing over the first pair of numbers. Future free-threading was a motivation, not a claim that this run already used it.

Round-three training was roughly four times faster end to end than the earlier setup, reaching about 50 positions per second per run. Iterations took around 210 seconds rather than roughly 300 in the preceding comparison. Those measurements use different reference points; the iteration-time ratio alone is not the source of the four-times claim.

Speed buys evidence

Faster training did not dissolve the later plateau. It bought more affordable iterations, ablations, and paired comparisons. That is still valuable: if an algorithm is not improving, learning that cheaply is better than learning it expensively. Throughput becomes a scientific instrument when it lets you distinguish a real gain from a noisy afternoon.

The project’s best optimization story is therefore not “we made everything instant.” It is that we measured the expensive path, reused valid work, batched the hardware-friendly part, and stopped duplicating accelerator ownership. The solver kept counting mines at an entirely respectable speed, relieved that nobody was demanding it outrun a few thousand CPU cycles anymore.
